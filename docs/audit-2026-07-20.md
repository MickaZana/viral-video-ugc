# End-to-End Application Audit — 2026-07-20

## Executive verdict

**Status: strong pre-production system; not ready for an evidence-backed general-availability claim.**

The local and mocked product is unusually well tested. Compilation succeeds, the full unit/integration suite succeeds, both browser suites succeed, media assembly is exercised with real ffmpeg output, and a fresh multi-platform dry run completed from discovery through the human review queue.

The remaining gap is not mainly code coverage. The product has not yet demonstrated its central commercial promise with funded live vendors and real customer publishing accounts. The repository's own P0 plan correctly keeps live vendor acceptance, provider OAuth, production operations, security/compliance review, and a three-cycle staging soak open. The marketing site currently describes several of those capabilities as present-tense facts and renders placeholder creator testimonials. Those claims should be qualified until live acceptance evidence exists.

## Scope and method

Audited:

- Monorepo structure, package scripts, application architecture, and documented product promises.
- TypeScript build, ESLint, unit/integration tests, dependency vulnerability audit.
- Orchestrator dry-run journey across TikTok and YouTube Shorts.
- Marketing-site and review-dashboard Playwright journeys.
- Authentication, authorization, tenant isolation, rate limiting, billing/quota, review, publishing gates, job handling, persistence, observability, accessibility, media assembly, and deployment configuration.
- README, architecture, launch/P0 plan, deployment workflow, and public marketing copy.

Not executed:

- Funded calls to Anthropic, Google/YouTube, TikTok, Meta, video vendors, voice vendors, Stripe production, or OpenAI ASR.
- Real OAuth consent, token refresh/revocation, or real publication.
- PostgreSQL integration tests (no `TEST_DATABASE_URL` was configured locally).
- Docker image build/runtime, Fly deployment, rollback, backup/restore, multi-worker crash recovery, or staging soak.

## Findings

### P0 — Claim/evidence mismatch

The marketing site states that the product is fully automated weekly, produces real video, fills a review queue on a predictable timeline, and supports an agency workload. The repository's launch plan says not to announce general availability until live acceptance, OAuth/publishing, operational hardening, security review, and three scheduled staging cycles pass.

The three creator-testimonial entries are explicitly `status: "placeholder"` but contain realistic handles, quotations, cost comparisons, automation claims, and a claim that the virality score tracks performance. Even if visually presented as placeholders, this is high legal/trust risk.

**Recommendation:** change present-tense capability claims to “designed to”/“in private beta,” label generated examples clearly, remove fictional testimonials, and publish measured reliability/latency/cost only after the launch gates pass.

### P0 — Production acceptance remains incomplete

No evidence in this audit proves:

- A live source can traverse every funded stage and produce an acceptable video.
- OAuth connects the correct real customer account and refreshes/revokes safely.
- Approval publishes exactly once to the intended destination.
- Actual cost and latency remain within defined limits.
- Three consecutive scheduled cycles reach clear terminal states.

**Recommendation:** execute `docs/remaining-p0-execution-plan.md` in order and retain acceptance artifacts, checksums, provider IDs, costs, timings, and human review decisions.

### P1 — CI is currently blocked by lint

`apps/review-dashboard/src/jobs.ts` imports `RunConfig` and `RunResult` but does not use them. Because CI runs lint before build/test, the current tree cannot pass the configured build-and-test job despite compilation and tests succeeding.

**Recommendation:** remove the unused imports and eliminate or explicitly tolerate the seven test-only `any` warnings.

### P1 — Production job behavior is not fully hardened

The implementation includes PostgreSQL job storage, leasing, heartbeat, recovery, retry, cancellation, and replay. The open P0 plan still calls for validating transactional claiming in the actual topology, jitter, retry classification, cancellation propagation, dead-letter UI/notifications, deterministic scheduler idempotency, and quota re-check immediately before spend.

The JSON fallback uses an unbounded spin while a lock file exists; a stale lock can hang the process indefinitely.

**Recommendation:** require PostgreSQL in production, fail closed rather than silently falling back, add bounded/jittered lock acquisition locally, and run kill/reclaim/two-worker/duplicate-enqueue chaos tests.

### P1 — Security launch controls remain incomplete

Positive evidence:

- Dashboard never runs unauthenticated.
- Secrets file `.env` is ignored and not tracked.
- Browser mutations reject explicit cross-origin requests.
- Social tokens have an encryption/rotation implementation.
- Publishing requires approval and checks for an existing provider post ID.
- Local tenant-isolation and auth tests are substantial.

Open launch controls, already acknowledged in the P0 plan:

- Named operator identities and fine-grained roles.
- Explicit CSRF tokens (origin checking is defense in depth, not a complete control).
- MFA, session revocation, security-event auditing.
- Data export/deletion and retention enforcement.
- Backup/restore/PITR drills.
- Threat models and adversarial tests for OAuth linking, signed media, prompt injection, malicious media, SSRF, and path traversal.
- Container scanning and unresolved-critical policy.

### P1 — Live integrations are contract-tested, not provider-proven

TikTok and Instagram discovery depend on provider approval. Facebook discovery is intentionally absent. Video, voice, ASR, and publishing adapters are primarily validated through mocks/contracts. This is honest in the README but less clear in marketing copy.

**Recommendation:** expose a capability matrix in the product/admin UI showing `mocked`, `configured`, `provider-approved`, and `live-accepted` states per tenant and integration.

### P2 — Quickstart portability

The README's comma-separated multi-platform command fails under the audited PowerShell/pnpm path.

**Recommendation:** document a Windows-safe invocation or change the CLI to accept repeated `--platform` flags in addition to comma-separated values.

### P2 — Test and operational hygiene

- The full suite emits very noisy request logs and generated-dashboard credentials, which makes CI failures harder to inspect.
- PostgreSQL tests are skipped without the CI service/environment, so a local green run does not cover the production store.
- Build results were Turbo cache hits; compilation still passed, but a clean-cache CI run remains the more authoritative signal.
- Dependency audit passed, but Node reported a deprecated `url.parse()` use in the dependency graph.

**Recommendation:** suppress/redact routine test logging, print a concise test summary, clearly report skipped integration suites, and trace/upgrade the deprecated dependency.

## What is ready now

- Local demonstration and product walkthroughs using dry-run data.
- Review-dashboard workflows, including filtering, bulk actions, approvals/rejections, account/team settings, simulated billing/quota, and tenant-isolated browser journeys.
- Marketing-site navigation, waitlist validation, video interactions, and baseline automated accessibility.
- Continued staged engineering and provider acceptance.

## What should not be claimed yet

- General production availability.
- Proven weekly delivery or “by Thursday” timing.
- Proven performance correlation from a virality score.
- Proven savings versus agencies.
- Live TikTok/Instagram/Facebook discovery across customer accounts.
- Reliable real-world auto-publishing across platforms.
- Customer testimonials unless they are genuine, permissioned, and attributable.

## Recommended release gates

1. Restore a green lint/CI gate.
2. Qualify marketing claims and remove placeholder testimonials.
3. Complete one funded YouTube-first live acceptance, including a forced ASR fallback and a forced vendor failure.
4. Complete real YouTube OAuth, refresh/revocation, approval, idempotent publishing, and correct-account verification.
5. Require PostgreSQL and demonstrate crash recovery, two-worker exclusion, retries, cancellation, and dead-letter operations.
6. Complete security/privacy controls and backup/restore testing.
7. Run at least three scheduled staging cycles over representative clients and publish measured completion, latency, cost, approval, and publishing rates.
8. Only then promote the marketing language from beta/design intent to measured capability.
