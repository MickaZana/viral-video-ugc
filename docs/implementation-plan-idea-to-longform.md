# Idea-to-Finished Long-Form Video: Implementation Plan

**Goal:** A user can provide an idea and optionally a viral-video pointer, choose a 5–10 minute 16:9 output and provider chain, and receive a reviewable finished video assembled from generated video, slides/images, and optional user-supplied screen recordings. When no screen recording is available, the system must create an animated illustrative visual and label it honestly.

**Current state:** 16:9 local assembly exists and has been tested with supplied assets. It accepts a JSON tutorial with local paths; it does not create a script, storyboard, assets, a persistent production job, or a user-facing result. The `LongFormTutorialSchema` currently allows 5–30 minutes and at most 100 scenes; the product requirement narrows this to 5–10 minutes and the scene limit must be raised or validated so five-second clips can cover ten minutes. The curriculum route currently routes long-form through a shorts pipeline capped at 60 seconds and records an asset without a rendered storage path. Higgsfield has an adapter requiring an injected MCP caller, but app background jobs do not currently provide one. Existing curriculum script-generation UI is a useful surface but has no source pointer, provider node, visual strategy, job progress, or result preview. The workspace already contains unrelated uncommitted work; all changes must preserve it.

**Provider funding snapshot (keys only; balances are not inferred):** Wan credential is present under `WAN3.0_API_KEY`, but region and free/paid quota are unverified; Replicate token is present but billing setup was observed as required; Higgsfield API/MCP credentials were not configured at the time of inspection, and the new background adapter only accepts a bearer token—it does not yet perform OAuth. `RUNWAY_API_KEY`, `FAL_KEY`, `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`, and `OPENAI_API_KEY` are present, but balances were not checked. Kling and xAI keys were absent. Runway's text-video adapter endpoint remains marked unverified; xAI's video adapter uses stale paths. Only Wan, Replicate, and explicitly connected Higgsfield are in this plan's default/optional long-form provider chain; other adapters are not declared production-ready by virtue of key presence.

## Product contract

- Output is 5–10 minutes (300–600 seconds), 16:9, 1920×1080, with continuous narration/music policy, captions, chapters, and a reviewable MP4 plus manifest.
- Input accepts a natural-language idea and an optional viral URL or pointer. The source is an inspiration for high-level structure, pacing, and rhetorical pattern; do not copy the source script, footage, identity, or distinctive expression.
- Planning agents produce an original, fact-aware full sequence, beat sheet, narration, visual prompts, and chapter timings. A pointer is optional; idea-only is a first-class path.
- A scene may use generated video, an authored slide, a generated still with camera/motion animation, or a user-provided screen recording. A missing/unavailable screen recording falls back to an animated image/diagram and receives an illustrative disclosure; never silently fabricate a real product UI or evidence.
- OpenAI/Claude/Gemini orchestration is bounded and observable. Every generated asset has an explicit provider/model, cost estimate/actual when available, status, retry limit, and source/provenance entry.
- Wan and Replicate are first-class configurable generation providers with ordered fallback. Higgsfield is an optional provider node the user explicitly selects in the production UI; it is not a required default/fallback unless configured.
- No automatic publishing. Completed output enters a human review state.
- Preserve the earlier short-form contract: each standard flow produces 2–4 shorts by default, each using a distinct original angle on the shared viral reference. Long-form is an explicit option from that flow to avoid surprising extra generation spend.
- Recursive improvement is limited to collecting outcomes and proposing prompt/config changes for human approval. The system cannot grant itself permissions, deploy code, alter provider/budget gates, or loop indefinitely.

## Execution and verification rules

1. Preserve all pre-existing working-tree changes. Before each atom, capture status and limit the diff to its declared files.
2. For every atom: declare criteria/risk/boundary, implement in isolation where feasible, run narrow deterministic validation, obtain an independent read-only verifier verdict, then integrate. Retry a change at most twice; escalate a rejected or high-risk atom for human review.
3. Run tests because successful E2E verification is explicitly requested. Keep provider calls mocked until the funded-canary atom.
4. Never expose key values. Do not claim account funds from key presence. Provider errors, source uncertainty, synthetic visuals, and AI narration must be represented honestly in the UI and artifact manifest.
5. A live canary must have an explicit numeric maximum spend supplied by the configured app/job cap and must stop when the provider's account state or cost estimate cannot be established safely. Before enabling it, record selected provider, matching region/model, dollar cap, credential presence only, and explicit approval for that capped attempt. Never include keys in logs or evidence.

## Exit criteria

The request is complete only when A9 passes in the app and produces a playable, reviewable 5–10 minute 16:9 video from an idea with no screen recording required; optional source-pointer and screen-recording inputs also pass. The standard flow still produces 2–4 distinct shorts by default and the optional long-form shares its source analysis. The UI exposes provider nodes and shows accurate job progress and result. Wan/Replicate orchestration and the optional Higgsfield MCP route have contract-tested failover. The market UI has desktop/mobile visual review evidence. Bounded improvement only proposes changes for human approval. A10 is reported separately if vendor billing access is unavailable; it must not be represented as successful live-provider verification without provider evidence. The live funded-provider proof remains separate because this repository cannot infer a balance from credentials and no vendor should be charged by ordinary CI or unit tests.
